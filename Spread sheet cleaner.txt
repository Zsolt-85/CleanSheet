CleanSheet
Master Business, Product, Marketing & Development Roadmap

Project type: Bootstrapped micro-SaaS
Initial product: Automated Excel/CSV data cleaning
Development approach: VS Code + Kilo Code / agentic coding
Initial objective: Build a reliable product capable of generating its first paying customers
First major business target: €300 MRR
Long-term objective: Build a low-maintenance recurring-income business and determine how far the opportunity can grow.
1. Our Founder Philosophy

CleanSheet is not being built with the assumption that it will become a huge startup.

We are building a small, useful internet business.

The initial objective is:

    Build something people genuinely find useful, get strangers to pay for it, and gradually turn that into recurring, low-maintenance income.

If the business eventually becomes much larger, excellent.

If it reaches €300–€500/month and requires very little ongoing work, that is already a successful outcome.

We will not confuse ambition with strategy.

The business will be developed according to:

Build → Measure → Learn → Improve → Monetize → Automate

We will not spend months building features based purely on assumptions.
2. The Core Business Hypothesis

Our hypothesis is:

    People and small businesses regularly receive messy Excel/CSV files and would pay for a simple tool that automatically identifies and fixes common data-quality problems.

The problem already has monetary value because people currently spend their own time or pay freelancers/services to perform data-cleaning work.

However:

The existence of the problem does not prove that our particular product will succeed.

Our job is to validate that.
3. Initial Product

The initial product should be extremely simple.

A user visits CleanSheet and sees:

    Clean your spreadsheet in seconds.

    Remove duplicates, fix messy formatting, validate your data and standardize your Excel or CSV file automatically.

    Upload your spreadsheet

The basic workflow:

User
 ↓
Uploads CSV/XLSX

 ↓

 ↓
User reviews/selects cleaning operations
 ↓

 ↓
Cleaned file generated
 ↓
Change report generated
 ↓
User downloads results

The user should understand the product within approximately five seconds.

7. AI Philosophy

The cleaning engine should primarily use deterministic algorithms.

Do NOT send entire spreadsheets to an LLM and ask:

    "Clean this spreadsheet."

Instead:

Spreadsheet
    ↓
Local profiler
    ↓
Deterministic rules
    ↓
Obvious problems fixed automatically
    ↓
Ambiguous problems identified
    ↓
AI used only where useful
    ↓
Confidence assessment
    ↓
User review where necessary

8. Deterministic Cleaning

Initial deterministic operations should include:

    duplicate row detection
    duplicate email detection
    empty row detection
    whitespace normalization
    basic capitalization normalization
    basic email validation
    safe date normalization
    basic value normalization
    spreadsheet profiling

These operations should be fast, cheap and predictable.
9. AI Features — Later

AI can eventually help with:

    identifying the semantic meaning of columns
    understanding unknown column names
    fuzzy/semantic duplicate detection
    category normalization
    ambiguous text normalization
    detecting relationships between columns
    suggesting cleaning rules

AI should be introduced only after the deterministic engine works reliably.
10. Change Tracking

Every automatic modification should be traceable.

Example:

Row: 82
Column: Email

Original:
" john @gmail.com "

New:
"john@gmail.com"

Reason:
Whitespace normalization

Rule:
email_whitespace_cleanup

The system should generate a structured change report.

Potential downloadable output:

cleaned_customers.xlsx
cleaning_report.xlsx

This is a major trust feature.

Users need to know:

    "What did your software actually change?"

11. Confidence Levels

Eventually, transformations can have confidence levels.
High confidence

Example:

    Exact duplicate email — 99.9%

Automatically fix.
Medium confidence

Example:

    Possible duplicate company — 82%

Ask the user or provide a review option.
Low confidence

Example:

    Possible category correction — 51%

Do not automatically modify.

The system must avoid confidently corrupting customer data.

20. Security Requirements

Uploaded files are untrusted input.

The application should implement:

    file type validation
    file size limits
    row limits
    column limits
    safe temporary file handling
    automatic temporary-file deletion
    safe error handling
    rate limiting
    no execution of uploaded content
    minimal logging of user data
    HTTPS in production

Initial example limits might be:

Maximum file size: 25 MB
Maximum rows: 50,000
Maximum columns: 200

These are starting points, not permanent limits.

58. Six-Month Decision Point

At approximately six months, evaluate honestly.
Scenario A — Nobody pays

Stop or pivot.
Scenario B — Small number of customers pay

Keep it as a micro-SaaS and improve gradually.
Scenario C — €300+ MRR

Strong validation.

Optimize retention and reduce maintenance.
Scenario D — €1,000+ MRR

Potentially significant micro-SaaS opportunity.

Consider specializing.
Scenario E — Strong growth and obvious demand

Consider turning it into a larger data-automation company.
59. Our "Kill / Continue / Double Down" Framework

Every approximately 30 days:
CONTINUE

People use it and some pay.

→ Continue improving.
DOUBLE DOWN

A particular customer segment strongly prefers it.

→ Focus heavily on that niche.
PIVOT

The problem exists but our solution isn't attractive.

→ Change the product or positioning.
KILL

Nobody cares enough to use or pay.

→ Stop spending time and move to another opportunity.
